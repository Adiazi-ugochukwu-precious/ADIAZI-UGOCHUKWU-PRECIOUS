Designing an idempotent ledger

Every naira that moves is one immutable row in an append-only ledger, and posting the same row twice is impossible. This is how I built that, and why.

01 / TL;DR

One rule for all money

I built NePay's money layer around one rule: every naira that moves is one immutable row in an append-only ledger, and posting the same row twice is impossible.

Each entry carries a referenceId idempotency key, backed by a unique index in Postgres. A retried webhook, a double tapped button or two racing workers all converge on the same row. Balances are never stored; they are computed as SUM(credits) − SUM(debits) on read. So there is no counter that can drift, and no update path that can corrupt history.

02 / The problem

Everything retries

NePay is a Nigerian wallet app from Circle Technology Limited, which I co-founded. Users fund an NGN wallet by bank transfer, crypto or USD virtual accounts, then withdraw to a bank or spend on airtime, bills, gift cards and flights. Almost every one of those flows depends on a third party that talks back asynchronously: bank rails, a USD account provider, a bill payments provider.

Those providers all retry. A webhook that times out on our side gets delivered again. A client on a bad mobile network resubmits. Two background jobs can reconcile the same purchase at the same moment. In a wallet, each of those is a potential double credit or double debit, and that is real money.

So the question I designed for was not “how do I record a transaction”. It was: how do I make it structurally impossible for the same money movement to land twice, no matter how many times or how concurrently it is attempted?

03 / Design principles

Five rules, set before any code

Every later module had to follow these.

  1. Append-only, enforced by structure.The ledger has no update or delete method. The one write path is an insert, never a save or upsert, so it can never take an UPDATE path. A mistake is fixed by posting an offsetting entry, never by editing history.
  2. Balances are derived, never stored.A wallet balance is the sum of its credits minus the sum of its debits, computed on read. There is no balance column to drift out of sync.
  3. Every entry carries an idempotency key.referenceId is required, and the database, not the application, guarantees it is unique.
  4. The database is the last line of defence.Rules that matter are constraints: a unique index on the key and a positive amount check. Application checks exist for speed and clearer errors, not for correctness.
  5. Side effects only after commit.Events are published after the transaction commits, so no listener ever reacts to money that did not persist.

04 / The data model

One table, one row per movement

The whole ledger is a single table. Each row is one movement of money against one wallet.

FieldTypeWhy it is shaped this way
walletIduuidIndexed with createdAt for fast statements

directionenumCREDIT or DEBIT. The direction carries the sign
amountnumeric(18,4)Always positive, checked by the database. A string in code, so no float ever touches it

The migration makes the key rules hard database facts:

ALTER TABLE ledger_entries
  ADD CHECK (amount > 0);

CREATE UNIQUE INDEX ON ledger_entries (reference_id);

Leaving out updatedAt was deliberate. Its absence tells the next engineer that this table is not meant to be edited.

05 / How idempotency works

Three layers, one real guarantee

Every module writes money through one method, postEntry(). It has three layers, and only the last one is the real guarantee.

  1. Validate at the door. No HTTP route reaches postEntry(); every caller is another service in the same process, so the global validation pipe never sees these calls. I validate the input inside the method and reject unknown fields. A bug in a caller cannot write a zero amount or an empty key into the ledger.
  2. Fast path pre-check. If an entry with this key already exists, return it. The caller sees the same success as the first time, and no second event fires.
  3. Race-safe insert. Two concurrent calls can both pass the pre-check. So the insert runs in a transaction, re-checks, and relies on the unique index. If Postgres raises 23505 (unique violation), I treat it as “someone else won”: fetch their row and return it as a normal result, not an error.

The design choice that matters most: a replay is a success, not an error. Webhook senders and mobile clients retry until they get a 2xx. If a duplicate raised an exception, every retry would look like a failure and cause more retries.

06 / Choosing the keys

Identify the event, not the attempt

The key has to identify the business event, not the attempt. I use the most stable ID available and derive follow-up keys from it.

FlowreferenceId
Bank deposit webhookThe provider's transaction reference
Withdrawal debitThe provider's transfer reference
Withdrawal fee<ref>-fee
Failed withdrawal refund<ref>-refund
Bill payment debit / refundOur UUID / <uuid>-refund
Discount / clawbackdiscount-<id> / discount-clawback-<id>

Derived suffixes turn one business event into a fixed set of entries. A failed withdrawal can be refunded at most once, however many times its webhook arrives.

07 / Serialising spend

Idempotency is not enough on its own

Idempotency stops the same movement landing twice. It does not stop two different withdrawals from spending the same balance.

For that, reserving a balance takes a Postgres transaction-scoped advisory lock on the wallet, pg_advisory_xact_lock(hashtext(walletId)). Inside that transaction it reads the balance on the same connection and creates a hold only if enough funds are available.

  • The lock covers one wallet only, so other wallets never wait.
  • Postgres releases it when the transaction ends, so a crash can never leave it stuck.

08 / Real flows

The design in real flows

Bank deposit webhook

A transfer into a user's virtual account arrives as a webhook. The handler finds the wallet and posts a deposit credit keyed on the provider's transaction reference. There is no separate status table, because nothing happens between “webhook received” and “wallet credited”. The ledger row is the record.

If the webhook arrives again, postEntry() returns the original row. The handler also checks whether the key exists first, so a replay does not send a second “wallet credited” notification. A deposit to an account we do not recognise is logged and dropped, not thrown. Throwing would make the provider retry forever.

Withdrawal

This flow has three levels of protection:

  • Before the provider call, a hold reserves the funds under the wallet lock, so two concurrent withdrawals cannot both pass the same balance check. Every exit path releases the hold exactly once.
  • After the provider call, the withdrawal row has a unique provider reference. If a retried request races itself, the losing call releases its own hold and returns the winner's record.
  • On the webhook, the state moves with a guarded update: UPDATE … WHERE id = ? AND status = 'PROCESSING'. Only the delivery that actually changes a row goes on to post a fee or a refund. Every other delivery sees zero affected rows and stops. The refund is also keyed <ref>-refund, so even a bug in that guard could not refund twice.

Bill payment: debit first, then call the provider

Bills work the other way round. I debit the wallet first, keyed on our own UUID, then call the bill payments provider. If it fails, a refund posts under <uuid>-refund. If it returns an unclear “processing” status, the debit stays in place until a scheduled requery, a webhook or an admin resolves it.

All three resolvers use the same guarded update and the same refund key. So a staff click and a scheduled run at the same moment cannot both refund. If the refund write fails after staff claim the row, the row goes back to PROCESSING so they can retry, and the key makes that retry safe even if the first write partly completed.

Rewards and clawbacks

A purchase discount is paid under discount-<id>. If the purchase is later reversed, the clawback reads that exact entry back and debits the same amount. It does not recompute from today's settings: if the discount percentage changed in between, recomputing would claw back the wrong amount.

09 / Failure modes

What stops each double movement

ScenarioWhat stops the double movement
A provider redelivers a deposit webhookSame transaction reference, so postEntry() returns the original row
Two copies of a webhook are processed at the same momentBoth pass the pre-check; the unique index lets one insert win, and the loser catches 23505 and returns the winner
Two withdrawals from one wallet at onceThe advisory lock on the wallet serialises the balance check and the hold
A retried withdrawal request races itselfUnique provider reference on the withdrawal; the loser releases its hold and returns the winner
A COMPLETED or FAILED webhook is replayedGuarded update on status = 'PROCESSING'; only the delivery that changes the row posts a fee or refund
A scheduled job, a webhook and an admin all resolve a stuck purchaseSame guarded update, same <id>-refund key
A refund write fails after a row is claimedThe row goes back to PROCESSING; a retry is safe because of the key
A caller bug sends a bad amountInput validation in postEntry(), plus the positive amount check in Postgres
A provider never sends the payout webhookThe status endpoint requeries the provider and feeds the result through the same idempotent handler
An entry was wrongPost an offsetting correction or adjustment; the original row stays

10 / Testing it

Test the contract, not just the happy path

The ledger's unit tests check its contract directly. For example:

  • a replay returns the existing entry without opening a transaction
  • a replay publishes no event
  • a duplicate payload cannot overwrite the original amount
  • a lost race returns the winner
  • errors other than a unique violation are re-thrown
  • the write goes through an insert, never a save or update
  • the event is published only after the transaction resolves

The bug a mock would never have found

One bug only showed up against real Postgres. For a wallet with no entries, SUM() returns NULL. An uncast 0 fallback then made the result an integer, so the balance came back as '0' instead of '0.0000'. I fixed it by casting both fallbacks, and added a test that checks the SQL itself:

SELECT
  COALESCE(SUM(amount) FILTER (WHERE direction = 'CREDIT'), 0::numeric(18,4))
- COALESCE(SUM(amount) FILTER (WHERE direction = 'DEBIT'),  0::numeric(18,4))
  AS balance
FROM ledger_entries
WHERE wallet_id = $1;  -- both fallbacks cast, or an empty wallet returns '0'

11 / Trade-offs

What it doesn't guarantee, written down

The ledger guarantees that money never moves twice. It gives weaker guarantees for side effects such as notifications, and I would rather write that down than hide it.

  • Events are not transactional yet. They are published after the commit on an in-process bus, so a crash between the two loses the event, never the money. The fix is a transactional outbox, and the event envelope already carries an ID, a version and a trace ID so that move stays small.
  • Duplicate notifications are narrowed, not eliminated. Checking the key first stops most replays from notifying twice, but two truly concurrent deliveries can both pass. That can cause a duplicate notification, never a duplicate credit.
  • Computed balances cost reads. A sum over every entry is exact and cannot drift, but it slows as history grows. The wallet and time index covers today's volume; the next step is periodic snapshots, where the balance is the last snapshot plus the entries since.
  • Single-entry, not double-entry. Each row changes one wallet. A full double-entry ledger would make reconciliation against provider statements a query instead of a report.

12 / Lessons

If you are building the same thing

  1. Put the idempotency guarantee in the database.Application checks are optimisations.
  2. Treat a duplicate as a success.Retrying clients need a 2xx back.
  3. Derive keys from the business event.<ref>-refund, not the attempt.
  4. Guard state changes with conditional updates.WHERE status = …, then check the affected row count.
  5. Never recompute money you already paid.Read the original entry back.
